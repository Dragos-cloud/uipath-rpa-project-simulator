RPA Project Simulator — User Guide

Version · XAML and PDD import · gap report · local LLM

Start with your project. Import supported UiPath™ workflow files and, optionally, a PDD to build a model for walkthroughs, exception reviews and documentation. Business analysts, RPA developers, stakeholders and trainers can explore the same project at different levels of detail. The built-in processes are examples for trying the controls. Parsing runs in this browser; optional AI features send context to your configured endpoint.

Independent community tool. UiPath™ is a trademark of UiPath, Inc. and UiPath SRL. This project is not affiliated with, sponsored by, or endorsed by UiPath. Import support is limited to the structures described in this guide; the app does not execute workflows or certify compatibility.

For your role: BAs review documented requirements and gaps; RPA developers inspect workflow relationships and exception handling; stakeholders discuss the process and human responsibilities; trainers guide a room through the steps and ask questions.

Getting started in 60 seconds

  1. Use Import project… to load your UiPath files and optional PDD, review the mappings, then build the simulation. To try the controls first, choose a built-in example from Project.
  2. Press Play. The diagram lights up step by step and the timeline on the right narrates what the robot is doing.
  3. When an amber Human action required card appears, the robot has stopped and is waiting for you. Click Done — continue to release it.
  4. Press Reset, choose something from Inject exception, and play it again.
  5. Scenario lets you choose recognized structured If/Else routes; other branches are skipped and dimmed. If no selectable route can be built, the control stays visible but disabled, with a reason. Flowchart decisions are not simulated as routes. All branches lists branches in document order, not one verified runtime path.
  6. On an imported project, ✦ Plain names asks the local model to rewrite developer-style step names and raw conditions in plain business language; the Plain names (AI) checkbox switches back to the original names at any time.

Scenario titles identify a route's activity focus. Branch details… explains the selected Boolean assumptions without an LLM, and lets you expand the full source condition and required True/Then or False/Else outcome. Unsupported expressions stay technical. Re-import older sessions if their conditions were already truncated. The walkthrough does not evaluate real runtime data.

Keyboard in the Simulator: Space play/pause, → single step, R reset. In this guide, use ←/→ to switch focused tabs and Home/End for the first/last topic.

Importing a real project

Press Import project… and select everything at once:

FileWhat is read from it
.xamlActivity tree, DisplayNames, annotations, Try/Catch, Throw messages, LogMessage text, and InvokeWorkflowFile links between files.
.csRegistered as a coded workflow. Its logic cannot be parsed, so the step appears as a black box and is flagged in the gap report.
.jsonSupported structured PDD export — sections, steps, exception tables, human intervention points, applications, test cases and operational details. Unrelated JSON is not treated as a PDD.
.docxWord document, not automatically a PDD. Supported headings and tables are read locally. Content and code/config references suggest whether it is requirements, an operational template, or needs review; you can override.
Config.xlsxAlso accepts Settings.xlsx and named variants. Reads Name/Value tables in Settings, Constants and Assets. Shows setting categories, source cells and supported links to imported documents/code. Most values are withheld; formulas, macros and external links are not executed.
.bpmnRead as a cross-check on task names.

Both PDD formats use the same validated internal documentation model. This validates the data structure, not the completeness or correctness of the requirements. Review document roles and choose one PDD, or continue without one. Among likely PDDs, JSON is the default priority; you can choose another. Documents are not compared or merged. Configuration is context, not requirements or verified runtime values. Review it again in Gaps → Project documents and configuration.

Click a process card to see Configuration used by this step in its inspector. It shows only recognized references for that workflow/activity and supported arguments passed directly by its caller. Expand Show where this comes from for the setting key, workbook cell and code reference. Duplicate values remain candidates, not a chosen runtime value. Old saved sessions need a source re-import.

In PDD readout → Document details and sources, review the optional document version, author, template identifier and scope. Values are labelled as provided, detected or unknown, with a JSON location or Word table/row reference when available. Missing details do not block import.

Older XAML files may need a browser-specific adjustment to their CLR namespace declarations. This happens only in memory, not in your source files or workflow logic. Check Gaps → Import review → Older XAML format accepted for affected files. Genuine XML errors are still reported; this does not prove runtime compatibility. Re-import files after an update.

The mapping step

After parsing, you are shown calls from Process.xaml or the declared entry workflow, with a suggested PDD requirement for each. Check these. The suggestions come from text similarity, which works when names share numbers or distinctive words and fails when a Romanian document meets English class names. Anything you leave unmatched is reported as a gap rather than quietly guessed.

Open PDD readout to inspect extracted target steps, typed BPMN elements, human-review requirements, rules, exception state transitions and table diagnostics. Legacy step tables and lane-oriented tables can use different column orders. A missing mapping or matching Throw is a review point, not proof of missing implementation.

Framework steps

REFramework plumbing — InitAllSettings, GetTransactionData, SetTransactionStatus, CloseAllApplications and friends — is collapsed into summary nodes by default so the business process stays readable. Tick Framework steps to expand them when someone asks how retries or queue statuses actually work.

The gap report

The Gaps button appears once a project is imported. It reports:

  • Exception coverage — supported raises mapped to model steps beside their closest documented counterpart, and vice versa, each with a similarity score. This is presented as evidence, not a verdict, because word-overlap scoring genuinely cannot do this job: in the reference project a true pairing scored 6% while a false one scored 32%. Read the tables yourself, or press Suggest pairings to have your local model propose semantic matches.
  • Sections with no implementation and workflows with no section — from the mapping you confirmed.
  • Order differences — where the document and the build disagree on sequence. The simulation always follows the XAML, because that is what actually runs.
  • Referenced workflows not supplied and non-XAML components — the limits of what this model can see.

Export the whole thing as Markdown for a review pack.

Durations are estimates. A XAML file records no timing information whatsoever. Step durations are derived from how much work each workflow contains and are marked estimated in the inspector. Treat the bot-vs-human split as a shape, not a measurement, until you have timings from an actual run.

Click any box to open the inspector — actor, system, duration, PDD reference, XAML reference, the activities inside the workflow and the log lines the robot writes.

The inspector sizes itself to its content within limits taken from your window, so a short step gets a compact panel and a long detail block gets a taller one. Drag the grip in its top-left corner to set your own size; double-click the grip to go back to auto-fit. Your size is remembered separately for small, medium and large windows, because a width that suits a laptop is wrong on an external monitor. The panel also flips to the left side on its own when it would otherwise cover the step you are looking at or the one currently executing.

Human participation

Human steps are first-class citizens in the model, not annotations. A step with gate: true stops the run completely and starts a timer. The time you take to click through is recorded as Human wait in the statistics bar, alongside Bot time.

This split is the most useful thing to put in front of a sceptical stakeholder. A process where the robot works for four minutes and then waits nine hours for someone to drop a file in a folder has a cycle-time problem that no amount of automation will fix. Run the simulation, let the gate sit open for a moment, and the point makes itself.

Injecting exceptions

Scenario derives a route from decision branches; it does not run their conditions. Inject exception arms a supported explicit raise mapped to a model step. Imported raises come from Throw activities or the supported literal-message throw new / Throw New subset in InvokeCode. Arbitrary inline code, variable throws and implicit activity failures are not exhaustively analysed. Included training processes use manually authored failures and responses.

Exception evidence separately lists code-defined Catch handlers, their protected Try activities, handler actions, simple literal status assignments, Finally and Rethrow. An empty injection list means no supported raise was mapped for injection, not that error handling is absent. A general System.Exception Catch handles a broad type; it does not identify a particular business or system failure.

The inventory covers all supplied XAML, including tests and workflows not proven reachable. Catch matching, type inheritance, caller propagation and successful recovery are not evaluated. An injected raise with a structurally enclosing Catch stops at Review required; the app does not invent the handler outcome. The evidence is also available in matching step inspectors, Gaps, Markdown export and generated PDD drafts.

Use Explain in Exception evidence for a business-language interpretation from your configured local model. Check the answer against the files; it is not a verified test result. Use Technical details to inspect source types and parser limits without AI.

Choosing an exception arms it. It fires once, at its trigger step, and the diagram redraws to show the handler path before you press play — so you can talk through the route with a stakeholder before running it.

System vs business exceptions

The included training models illustrate the following design patterns. These are not guarantees about imported projects or platform runtime behaviour:

System exceptionBusiness exception
CauseThe environment misbehavedThe data is wrong
RetryYes — often recoversNo — identical data fails identically
Queue statusFailed (Application)Failed (Business Rule)
Goes toRPA supportThe business team

What you will see

  • Retry loops — the handler steps run, then the failed step is re-attempted, marked re-attempt in the timeline.
  • Recovery — some exceptions clear on the final retry and rejoin the main flow. Try SAP not responding or ServiceNow API timeout. Worth showing to anyone who believes every logged error means a failed process.
  • Resume — the transaction is abandoned but the run continues with the next queue item. Try PO number not found.
  • Terminal stop — the whole run halts. Try SAP credential expired, Duplicate payroll record or Duplicate AD account exists.
  • Human escalation inside a handler — exception paths can contain their own gates, for the rare case where the robot genuinely needs an answer before it can continue. None of the built-in scenarios needs one: a person who only has to be told (the AP clerk, RPA support, HR) is notified without the robot waiting.

Local LLM (LM Studio)

The simulator can call a model running on your own machine to explain steps and brief you on a process. AI requests send process context to the endpoint you configure. Use a local or otherwise approved endpoint for sensitive process material; a remote endpoint can send that context outside your machine or network.

Setup

  1. Open LM Studio and load a model. Anything in the 7B–14B instruct range is more than adequate for this; larger models are slower without being noticeably better at it.
  2. Go to the Developer tab and click Start Server.
  3. In the server settings, enable CORS. This is the step people miss — without it the browser silently blocks every request from this page.
  4. Click the chip at the top-right of this app, press Test, choose your model, and Save.

If your server requires a token

Some LM Studio setups — particularly when it is fronted by a proxy, or when you have set an API key in its server settings — reject unauthenticated requests. Put the key in the API token field and it is sent as Authorization: Bearer <token> on every request, including the model list. A plain local server needs nothing here.

Leave Remember this token in the browser unticked and the token is held in memory for the session only, so it never touches local storage. Tick it and it is saved alongside the other settings — convenient on your own machine, less so on a shared one. Disable clears it.

A 401 or 403 is reported as a credentials problem rather than a generic connection failure, so you can tell an authentication issue apart from a CORS or server-not-running one.

If Test fails. Confirm the server is running at http://localhost:1234/v1 (LM Studio shows the exact URL). Confirm CORS is enabled. If you opened this file directly from disk the browser origin is null, which LM Studio accepts with CORS on but some other servers reject.

What it does

  • ✦ Explain in the step inspector — explains the selected step, what breaks without it, and one thing to check when documenting it.
  • ✦ Brief me above the timeline — a pre-run briefing covering what the robot achieves, where humans remain and which exception most threatens the business case.
  • Ask — ask a question about the current project using the supplied process context.
  • ✦ Plain names — rewrite eligible imported step and decision labels in business language; switch back to the originals with the checkbox.
  • Suggest pairings in the gap report — propose matches between coded and documented exceptions.

Set the audience in the settings modal. The same step explained for a stakeholder and for a developer produces usefully different answers. Check AI output against the project sources; it may be incomplete or incorrect.

The Process Model format

Load session… and Save session… move process models in and out as JSON. The project importers build this same model from the supplied files, within the parser's limits.

{
  "meta": { "id":"my-process", "name":"...", "description":"...", "source":"..." },
  "steps": [
    { "id":"s1",
      "name":"Post invoice in SAP",
      "actor":"bot",            // bot | human | system
      "app":"SAP GUI",
      "ms":7800,                // simulated duration
      "gate":false,             // true = halt and wait for the user
      "gatePrompt":"...",       // shown on the amber card
      "branch":"main",          // main | exception
      "detail":"plain-English description",
      "log":"line the robot writes to Orchestrator",
      "source":{ "pdd":"§4.6", "xaml":"Process.xaml > Post Invoice" } }
  ],
  "exceptions": [
    { "id":"e1",
      "name":"SAP not responding",
      "class":"system",         // system | business
      "trigger":"s9",           // step id where it fires
      "retry":{ "count":3 },
      "retryPath":["x1","x2"],  // steps run before each retry
      "recovers":true,          // succeeds on the final attempt
      "path":["x3","x4"],       // steps run once retries are exhausted
      "resume":"s6",            // rejoin the main flow here
      "terminal":false,         // true = stop the run
      "detail":"what a BA should understand about this failure",
      "source":"xaml" }         // xaml | pdd | user
  ]
}

Rules worth knowing: exception handler steps live in steps[] with "branch":"exception"; an exception fires only once per run; terminal beats resume; and omitting retry means the handler runs immediately, which is the correct shape for a business exception.

Suggested training exercises

  1. Run the invoice process clean. Ask the group where the robot is actually saving time, then show them the Bot time and Human wait figures.
  2. Inject SAP not responding. Ask whether this counts as a failure. Most people say yes; the recovery step shows otherwise.
  3. Inject PO number not found. Ask what happens to the invoices behind it in the queue — watch the decision loop pick up the next one. This is the question that justifies queue-based design.
  4. Inject Inbound folder is empty. Ask whether anyone should be alerted at 6am on a bank holiday.
  5. Inject SAP credential expired. Ask where password rotation appears in the PDD. It usually does not.
  6. Switch to onboarding and inject Duplicate AD account. Ask why the robot halts instead of waiting for HR, and who restarts the onboarding afterwards.

Importul unui proiect real

Ambele formate PDD folosesc același model intern validat al documentației. Validarea verifică structura datelor, nu caracterul complet sau corectitudinea cerințelor. Verifică rolurile și alege un singur PDD sau continuă fără. Dintre PDD-urile probabile, JSON are prioritate implicită; poți alege altul. Documentele nu sunt comparate sau îmbinate. Configurația oferă context, nu cerințe sau valori verificate la rulare. O poți revedea în Diferențe → Documentele și configurația proiectului.

Apasă pe un card pentru a vedea Configurația folosită de acest pas în panoul de detalii. Sunt afișate doar referințele recunoscute din acel workflow/activitate și argumentele suportate transmise direct de apelant. Extinde Vezi de unde provine informația pentru cheia setării, celula sursă și codul. Valorile duplicate rămân candidați, nu o valoare aleasă la rulare. Sesiunile vechi necesită reimportul surselor.

În Conținut PDD → Detalii și surse ale documentului poți verifica versiunea documentului, autorul, identificatorul șablonului și aria documentului. Valorile sunt marcate ca furnizate, detectate sau necunoscute, cu locația JSON ori tabelul/rândul Word când sunt disponibile. Lipsa acestor detalii nu blochează importul.

Fișierele XAML vechi pot necesita adaptarea declarațiilor de namespace CLR la cerințele browserului. Adaptarea are loc doar în memorie, fără modificarea fișierelor sursă sau a logicii. Verifică Diferențe → Verificarea importului → Format XAML vechi acceptat pentru lista fișierelor. Erorile XML reale sunt raportate în continuare; aceasta nu dovedește compatibilitatea la rulare. Reimportă fișierele după actualizare.

Pasul de corespondență

După analiză vezi apelurile din Process.xaml sau workflow-ul de intrare declarat, cu o cerință PDD sugerată. Verifică-le. Sugestiile provin din similaritate textuală, care funcționează când denumirile împart numere sau cuvinte distinctive și eșuează când un document în română întâlnește denumiri de clase în engleză. Ce rămâne nepotrivit este raportat ca diferență, nu ghicit în tăcere.

Deschide Conținut PDD pentru pași, elemente BPMN tipizate, cerințe de intervenție umană, reguli, tranziții de stare și diagnosticul tabelelor. Tabelele vechi și cele organizate pe roluri pot avea coloane în altă ordine. Lipsa unei asocieri sau a unui Throw corespondent necesită verificare și nu dovedește lipsa implementării.

Pașii de framework

Infrastructura REFramework — InitAllSettings, GetTransactionData, SetTransactionStatus, CloseAllApplications și celelalte — este pliată implicit în noduri-rezumat, ca procesul de business să rămână lizibil. Bifează Pași framework pentru a le extinde când cineva întreabă cum funcționează efectiv reîncercările sau statusurile din coadă.

Raportul de diferențe

Butonul Diferențe apare după importul unui proiect. Raportează:

  • Acoperirea excepțiilor — fiecare excepție aruncată în cod alături de cea mai apropiată excepție documentată, și invers, fiecare cu un scor de similaritate. Sunt prezentate ca dovezi, nu ca verdict, fiindcă potrivirea pe cuvinte comune chiar nu poate face această treabă: în proiectul de referință o pereche corectă a obținut 6%, iar una greșită 32%. Citește tabelele singur sau apasă Propune corespondențe pentru ca modelul local să sugereze potriviri semantice.
  • Secțiuni fără implementare și workflow-uri fără secțiune — pe baza corespondenței confirmate de tine.
  • Diferențe de ordine — unde documentul și implementarea nu coincid ca secvență. Simularea urmează întotdeauna codul XAML, pentru că acela rulează efectiv.
  • Workflow-uri referite, dar nefurnizate și componente non-XAML — limitele a ceea ce acest model poate vedea.

Totul poate fi exportat în Markdown pentru un pachet de review.

Duratele sunt estimări. Un fișier XAML nu conține absolut nicio informație de timp. Duratele pașilor sunt derivate din cantitatea de activități din fiecare workflow și sunt marcate estimated în panoul de detalii. Tratează raportul robot/om ca pe o formă, nu ca pe o măsurătoare, până ai timpi dintr-o rulare reală.

Participarea umană

Pașii umani sunt elemente de sine stătătoare în model, nu adnotări. Un pas cu gate: true oprește complet rularea și pornește un cronometru. Timpul până apeși butonul este înregistrat ca Așteptare om în bara de statistici, alături de Timp robot.

Această separare este cel mai util lucru pe care îl poți pune în fața unui factor de decizie sceptic. Un proces în care robotul lucrează patru minute și apoi așteaptă nouă ore ca cineva să pună un fișier într-un folder are o problemă de durată de ciclu pe care nicio automatizare nu o rezolvă. Rulează simularea, lasă cardul portocaliu deschis un moment, și argumentul se susține singur.

Injectarea excepțiilor

Scenariu derivă un traseu din ramurile deciziilor, fără a le executa condițiile. Injectează excepție armează o declanșare explicită suportată, asociată unui pas. La import sunt recunoscute activitățile Throw și un subset cu mesaj literal throw new / Throw New din InvokeCode. Codul arbitrar, aruncările prin variabile și erorile implicite ale activităților nu sunt analizate exhaustiv. Procesele de instruire incluse folosesc erori și răspunsuri definite manual.

Dovezi excepții listează separat blocurile Catch definite în cod, activitățile Try protejate, acțiunile de tratare, atribuirile simple de status literal, Finally și Rethrow. O listă de injectare goală înseamnă că nu s-a asociat o declanșare suportată pentru injectare, nu că tratarea erorilor lipsește. Un Catch general System.Exception nu identifică o anumită eroare de business sau de sistem.

Inventarul include toate fișierele XAML furnizate, inclusiv teste și workflow-uri a căror accesibilitate nu este demonstrată. Selectarea Catch, moștenirea tipurilor, propagarea către apelant și revenirea reușită nu sunt evaluate. O declanșare injectată cu un Catch structural înconjurător se oprește la Review required; aplicația nu inventează rezultatul tratării. Dovezile apar și în inspectorii pașilor corespunzători, în Diferențe, în exportul Markdown și în schițele PDD generate.

Folosește Explică din Dovezi excepții pentru interpretarea în limbaj de business oferită de modelul local configurat. Verifică răspunsul în fișiere; nu este un rezultat de test validat. Detalii tehnice arată tipurile din sursă și limitele parserului, fără AI.

Alegerea unei excepții o armează. Se declanșează o singură dată, la pasul ei, iar diagrama se redesenează pentru a arăta traseul de tratare înainte să apeși rulează — poți astfel discuta traseul cu un stakeholder înainte de a-l executa.

Ce vei observa

  • Bucle de reîncercare — pașii de tratare rulează, apoi pasul eșuat este reîncercat, marcat re-attempt în cronologie.
  • Revenire — unele excepții se rezolvă la ultima reîncercare și revin pe fluxul principal. De arătat oricui crede că orice eroare din log înseamnă proces eșuat.
  • Reluare — tranzacția este abandonată, dar rularea continuă cu următorul element din coadă.
  • Oprire definitivă — întreaga rulare se oprește.
  • Escaladare umană în tratare — traseele de excepție pot conține la rândul lor pași de așteptare.

Model LLM local (LM Studio)

Simulatorul poate apela un model care rulează pe calculatorul tău pentru a explica pași și a-ți prezenta procesul. Cererile AI trimit contextul procesului către endpoint-ul configurat. Pentru date sensibile, folosește un endpoint local sau aprobat; un endpoint la distanță poate trimite contextul în afara calculatorului sau rețelei.

  1. Deschide LM Studio și încarcă un model. Orice model instruct de 7B–14B este suficient aici.
  2. Mergi la fila Developer și apasă Start Server.
  3. În setările serverului, activează CORS. Acesta este pasul care se uită cel mai des — fără el, browserul blochează în tăcere orice cerere din această pagină.
  4. Apasă pastila din dreapta sus, apasă Test, alege modelul și Save.

Dacă serverul cere un token

Unele configurații LM Studio — mai ales când există un proxy în față sau când ai setat o cheie API în setările serverului — resping cererile neautentificate. Pune cheia în câmpul API token și va fi trimisă ca Authorization: Bearer <token> la fiecare cerere, inclusiv la listarea modelelor. Un server local simplu nu are nevoie de nimic aici.

Dacă lași nebifat Remember this token in the browser, tokenul este păstrat doar în memorie pe durata sesiunii și nu ajunge niciodată în local storage. Bifat, este salvat împreună cu celelalte setări — comod pe calculatorul propriu, mai puțin pe unul partajat. Disable îl șterge.

Un răspuns 401 sau 403 este raportat ca problemă de credențiale, nu ca eroare generică de conexiune, ca să poți distinge o problemă de autentificare de una de CORS sau de server oprit.

Funcții: ✦ Explain în panoul de detalii, ✦ Prezintă-mi deasupra cronologiei, Întreabă despre proiectul curent, ✦ Nume simple pentru etichete eligibile din proiecte importate și Propune corespondențe în raportul de diferențe. Alege audiența în setări și verifică răspunsurile AI în sursele proiectului; pot fi incomplete sau incorecte.

Formatul Process Model

Încarcă sesiune… și Salvează sesiune… transferă modelul procesului ca JSON. Importul proiectului construiește același model din fișierele furnizate, în limitele parserului.

{
  "meta": { "id":"procesul-meu", "name":"...", "description":"...", "source":"..." },
  "steps": [
    { "id":"s1", "name":"Înregistrează factura în SAP",
      "actor":"bot",            // bot | human | system
      "app":"SAP GUI", "ms":7800,
      "gate":false,             // true = așteaptă confirmarea utilizatorului
      "gatePrompt":"...", "branch":"main",
      "detail":"descriere pentru business", "log":"mesaj de log",
      "source":{ "pdd":"§4.6", "xaml":"Process.xaml > Înregistrează factura" } }
  ],
  "exceptions": [
    { "id":"e1", "name":"SAP nu răspunde", "class":"system",
      "trigger":"s1", "retry":{ "count":3 },
      "retryPath":["x1","x2"], "recovers":true,
      "path":["x3","x4"], "resume":"s6", "terminal":false,
      "detail":"semnificația excepției pentru BA", "source":"xaml" }
  ]
}

Exemplu de structură: identificatorii din trasee trebuie să corespundă unor pași reali din model. Pașii de tratare stau în steps[] cu "branch":"exception". O excepție se declanșează o singură dată pe rulare; terminal are prioritate față de resume; fără retry, tratarea începe imediat.

Exerciții de instruire sugerate

  1. Rulează procesul curat. Întreabă grupul unde economisește robotul timp, apoi arată cifrele Timp robot și Așteptare om.
  2. Injectează o excepție de sistem care își revine. Întreabă dacă asta contează ca eșec. Majoritatea spun da; pasul de revenire arată contrariul.
  3. Injectează o excepție de business. Întreabă ce se întâmplă cu restul fișierelor.
  4. Injectează cazul „folder gol”. Întreabă dacă cineva ar trebui alertat la 6 dimineața într-o zi liberă.
  5. Deschide raportul de diferențe și întreabă cine ar fi trebuit să observe excepțiile nedocumentate — și în ce moment al proiectului.
