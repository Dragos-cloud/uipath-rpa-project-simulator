# Project working agreements

## Visual-first change proposals

- Before implementing a feature or change that is easier to understand visually, show a preview in the conversation. Use a mock-up for screens/cards/reports/document layouts, a flow diagram for workflows, or a before/after comparison for other visual changes.
- Match the existing product's appearance and use one concrete example throughout. Prefer a small, readable preview; make it clickable when interaction or changing states are important. Offer alternatives only when they help the user make a real decision.
- Clearly label proposed designs, illustrative data and example AI responses. Do not present a mock-up as an implemented feature, a verified result or an actual model response.
- Explain in plain language what the user will see, what changes and what stays the same. Describe checks in practical terms (for example, "the template appears on the correct step" or "passwords do not appear in exports"), not only as "validate and document."
- Obtain approval of the visual direction before changing application code, unless the user has already approved the relevant preview or explicitly asks to skip it. Planning/preview-only requests must not change the application.
- Use the smallest useful visual. Do not invent a mock-up for invisible maintenance, or turn a trivial wording change into a design exercise; use a short before/after when helpful.
- After approval, implement the agreed design and verify that the actual result matches it. Flag material departures before implementing them. A mock-up is not proof that the feature works.
